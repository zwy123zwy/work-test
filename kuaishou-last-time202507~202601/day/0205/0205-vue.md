## 1. Vue 2 和 Vue 3 响应式原理的区别？为什么 Vue 3 用 Proxy？

### 答案要点

**Vue 2：Object.defineProperty**

- 在 data 初始化时遍历对象，对每个属性用 `Object.defineProperty` 做 getter/setter 劫持。
- **局限**：
  - 无法监听**新增属性**（需 `Vue.set`/`this.$set`）。
  - 无法监听**数组下标赋值**（如 `arr[i]=x`）和 `arr.length` 修改；通过重写数组 7 个方法（push、pop、shift、unshift、splice、sort、reverse）做「拦截」来触发更新。
  - 必须**深度遍历**对象，初始化时递归一次，性能与可维护性一般。
- **本质**：针对「已有属性」的读写做劫持，无法感知「有没有这个 key」。

**Vue 3：Proxy**

- 用 `new Proxy(target, handler)` 代理整个对象，在 handler 的 `get`/`set`/`deleteProperty`/`has` 等里做依赖收集与派发更新。
- **优势**：
  - **新增、删除属性**都能被监听到，无需 `$set`。
  - **数组**任意下标读写、length 修改、新方法都可被代理。
  - 可代理 **Map/Set/WeakMap/WeakSet** 等，Vue 2 做不到。
  - 懒代理：访问到嵌套对象时再递归代理（按需），减少初始化开销。
- **本质**：在「对象级别」做代理，任何对对象的访问/修改都会经过 handler，因此能覆盖新增、删除、数组等场景。

**总结**：Vue 3 用 Proxy 是为了解决 Vue 2 响应式在「新增/删除属性、数组」上的缺陷，并提升可扩展性（如 Ref、reactive、readonly 等统一基于 Proxy）。

## 2. 说下 Vue 的生命周期（Vue 2 / Vue 3）以及各自在什么场景用？

### 答案要点

**Vue 2 选项式生命周期（常用）**

| 钩子 | 时机 | 典型用途 |
|------|------|----------|
| beforeCreate | 实例初始化后，data/methods 未注入 | 很少用 |
| created | 实例创建完成，data、computed、methods 可用，未挂载 DOM | 请求接口、初始化非响应式数据 |
| beforeMount | 挂载前，render 首次执行完，DOM 尚未替换 | 很少用 |
| mounted | 挂载完成，DOM 可访问 | 访问/操作 DOM、初始化第三方库、订阅、定时器 |
| beforeUpdate | 数据变更导致虚拟 DOM 重渲染前 | 需要拿到「更新前」的 DOM 时 |
| updated | 虚拟 DOM 打补丁后，DOM 已更新 | 依赖新 DOM 的操作（注意避免在 updated 里改数据，易死循环） |
| beforeDestroy | 实例销毁前 | 解绑事件、清定时器、取消订阅 |
| destroyed | 实例销毁后 | 收尾逻辑 |

**Vue 3 组合式（Composition API）对应关系**

- `setup()` 本身在 **beforeCreate 之前**执行，相当于「created 之前」的逻辑写在 setup 里。
- 没有 beforeCreate/created 的显式钩子，用 `onBeforeMount`、`onMounted`、`onBeforeUpdate`、`onUpdated`、`onBeforeUnmount`、`onUnmounted` 等（Vue 3 中 destroyed 改名为 unmount）。
- `onMounted` ≈ mounted；`onUnmounted` ≈ beforeDestroy + destroyed 的清理时机。

**注意**：在 setup 或 Composition API 里请求数据，通常放在 `onMounted` 或直接在 setup 顶层用 async（配合 Suspense 或外层处理 loading），避免在未挂载时访问 DOM。

## 3. v-model 本质是什么？Vue 3 里和 Vue 2 有什么不同？

### 答案要点

**本质**

- **语法糖**：`:value`（或 `:modelValue`）+ `@input`（或 `@update:modelValue`）。
- 组件上：`v-model="x"` 等价于  
  `:modelValue="x"` + `@update:modelValue="x = $event"`。

**Vue 2**

- 默认用 `value` + `@input`；可通过 `model` 选项改成别的 prop 名和事件名（如 `model: { prop: 'checked', event: 'change' }`）。
- 一个组件只能有一个 `v-model`。

**Vue 3**

- 默认用 `modelValue` + `@update:modelValue`。
- **多个 v-model**：`v-model:title="title"` 即 `:title="title"` + `@update:title="title = $event"`，可写多个。
- **自定义修饰符**：通过 `modelModifiers`（默认）或 `titleModifiers`（v-model:title）在组件内拿到，如 `v-model.trim` 时可在内部对输入做 trim。

**自定义组件示例（Vue 3）**

```vue
<!-- 父组件 -->
<MyInput v-model="text" />
<MyInput v-model:value="text" v-model:caption="cap" />

<!-- 子组件内部 -->
props: ['modelValue'],  // 或 ['value', 'caption']
emits: ['update:modelValue'],  // 或 ['update:value', 'update:caption']
// 输入时：emit('update:modelValue', newVal)
```

## 4. Vue 的 nextTick 是做什么的？实现思路？

### 答案要点

**作用**

- 在「本次 DOM 更新周期」之后执行回调，用于在数据变更后拿到**更新后的 DOM**，或把逻辑推迟到下一轮更新后执行。

**典型场景**

- 数据改完后需要基于新 DOM 做测量或操作（如 focus、scrollHeight）。
- 在子组件或列表渲染后做一次性计算。

**实现思路（Vue 3 以 Promise 为主）**

1. 维护一个队列，把用户传入的回调推进队列。
2. 在「当前 tick」内只执行一次「 flush 函数」：遍历队列执行回调并清空。
3. **降级顺序**：`Promise.then` → `MutationObserver` → `setImmediate` → `setTimeout`，用微任务（或宏任务）在本次渲染/下一轮 DOM 更新后执行 flush。
4. `await nextTick()` 可配合 async 使用，保证在「下一 tick」之后再执行后续代码。

**注意**：nextTick 不保证「浏览器已经完成绘制」，只保证 Vue 的虚拟 DOM 已打补丁到真实 DOM；若需「绘制后」再执行，可再包一层 `requestAnimationFrame` 或 `setTimeout(fn, 0)`。

## 5. 组件间通信方式有哪些？各适合什么场景？

### 答案要点

| 方式 | 适用场景 | 说明 |
|------|----------|------|
| props / emit | 父子、单向数据流 | 父 → 子 props；子 → 父 emit；简单清晰，优先使用 |
| v-model / .sync | 父子双向绑定 | 语法糖，本质仍是 props + emit |
| ref + expose | 父调子方法或访问子实例 | 父组件 ref 子组件，子用 defineExpose 暴露方法或数据；Vue 3 推荐 |
| provide / inject | 祖先 → 后代（跨层） | 不限制层级；适合主题、locale、全局配置；注意不是响应式时用 ref/reactive 包一层 |
| EventBus（全局事件） | 任意组件 | Vue 2 常见，Vue 3 可用 mitt/tiny-emitter；易导致难以维护，中大型项目慎用 |
| Vuex / Pinia | 全局/多组件共享状态 | 复杂状态、多组件共享、需要 devtools 时用 |
| slot / 作用域 slot | 父定制子内容 | 布局、UI 定制；作用域插槽可把子组件数据回传给父 |
| attrs / listeners（Vue 2） | 透传未声明属性/事件 | 写高阶组件、封装第三方组件时透传 |
| $attrs / $listeners（Vue 3 合并为 $attrs） | 同上 | Vue 3 中 class、style、事件都会进 $attrs，可配合 inheritAttrs: false 精细控制 |

**建议**：能父子解决的用 props/emit；跨多层用 provide/inject；全局共享用 Pinia/Vuex；避免滥用 EventBus。

## 6. Vue 的 key 为什么推荐用唯一 id 而不是 index？diff 时 key 起什么作用？

### 答案要点

**key 在 diff 中的作用**

- 在 **sameVNode** 判断中，若 tag 和 key 都相同，才认为是同一节点，可复用并做 patch；否则视为不同节点，可能删除旧节点、新建新节点。
- 列表 diff 时，通过 key 建立「旧 children 与新 children」的对应关系，尽量复用 DOM，减少不必要的删除/创建。

**为什么不用 index 做 key？**

- 列表**顺序会变**（排序、过滤、前插、删除）时，index 会整体错位。
- 例如：原来 [A,B,C] 对应 index 0,1,2；删除 A 后变成 [B,C]，B 的 index 变成 0，C 变成 1。Vue 会认为「0 还是 0、1 还是 1」，复用了错误的 DOM，导致状态错乱（如 B 的勾选状态跑到 C 上）、性能也未必最优（本可复用 B、C 的 DOM，却可能误删误建）。
- 用**唯一 id**（如 item.id）则删除 A 后，B、C 的 key 不变，能正确复用并保持组件内部状态。

**结论**：key 要稳定、唯一，与「当前项」一一对应；有 id 用 id，无 id 可用业务唯一标识，避免用 index，尤其在列表会增删改序时。

## 7. 说说 Vue 的 computed 和 watch 的区别与使用场景？

### 答案要点

**computed**

- **有缓存**：依赖的响应式数据不变，多次访问只算一次。
- **必须有返回值**，适合「派生状态」「格式化展示」。
- 默认只读；Vue 3 可写 computed（get + set）实现双向派生。
- 使用场景：过滤列表、金额/日期格式化、多字段组合成一个展示值。

**watch**

- **无缓存**，监听某个（或多个）源，变化就执行回调。
- 可拿到 **oldVal / newVal**，适合「副作用」：请求接口、操作 DOM、写本地存储、打点。
- 支持 `immediate`、`deep`；Vue 3 还可 `watchEffect`、`watch([a, b], ...)` 多源。
- 使用场景：路由参数变化拉接口、表单联动、防抖请求、离开页面前提示保存。

**对比**

|  | computed | watch |
|--|----------|--------|
| 目的 | 派生一个值 | 响应变化做副作用 |
| 缓存 | 有 | 无 |
| 返回值 | 必须有 | 无要求 |
| 典型用法 | 模板里当属性用 | 数据变时调接口、改别的数据 |

## 8. Vuex 和 Pinia 的区别？为什么 Vue 3 推荐 Pinia？

### 答案要点

**Vuex（Vue 2 时代标配）**

- 概念：state、getters、mutations、actions、modules。
- 同步改状态必须通过 **mutations**；异步或复杂逻辑放在 **actions** 里再 commit mutation。
- modules 需要命名空间，且 getter/action 的类型推导和 TS 支持一般。
- 与 Vue 3 组合式 API 一起用时，要 `useStore()` 再取 state/commit/dispatch，略啰嗦。

**Pinia**

- **无 mutations**：在 actions 里直接改 state（同步或异步都行），更符合直觉。
- **无 modules**：用多个 store 文件（每个 defineStore 一个 store），通过 store 组合而不是一棵大树，更清晰。
- **TS 友好**：类型推导好，定义 store 即得类型。
- **与 Composition API 一致**：在 setup 里 `const store = useXxxStore()`，直接用 store.xxx、store.actions，配合 computed 即可。
- 体积小、API 简单，官方推荐为 Vue 3 默认状态管理。

**迁移**：Vuex 的 state → Pinia state；getters → Pinia getters 或 computed；mutations 可合并进 actions；actions 对应 Pinia actions；modules 拆成多个 defineStore。

## 9. Vue 的 keep-alive 原理？如何配合路由做缓存？

### 答案要点

**作用**

- 用 `<keep-alive>` 包裹动态组件或 router-view 时，被包裹的组件在切换时**不会销毁**，而是被缓存到内存（LRU 等策略），再次切回时从缓存恢复，不重新执行 mounted。

**原理简述**

- keep-alive 是抽象组件，不渲染真实 DOM，只渲染其默认插槽的第一个子组件。
- 通过 **cache**（如 Map）以组件 name 或 slot 的 key 为键，存 vnode 或组件实例；切换时若命中缓存则从缓存取并恢复（如恢复 DOM、更新 props），否则才挂载新实例并加入缓存。
- 可配置 **include / exclude / max**（Vue 3）：只缓存匹配的组件、排除某些组件、最大缓存数量（超出时按 LRU 淘汰）。

**配合 Vue Router**

- 在 layout 里用 `<router-view v-slot="{ Component }">` 包一层 `<keep-alive>`，用 `include` 指定要缓存的组件 name（与路由组件 name 一致）。
- 或根据路由 meta.keepAlive 动态决定是否包 keep-alive，实现按路由缓存。
- 被缓存组件可用 **activated / deactivated** 钩子做「每次显示/隐藏」时的逻辑（如刷新列表、暂停动画）。

## 10. Vue 3 的 Composition API 和 Options API 对比？为什么要有 Composition API？

### 答案要点

**Options API**

- 按选项组织：data、methods、computed、watch、生命周期等分散在不同选项里。
- 同一块「逻辑」可能拆在 data + methods + mounted 等多处，逻辑分散；多个逻辑混在一起时难以抽离和复用。

**Composition API（setup + 组合函数）**

- 按「逻辑」组织：一个功能用一组 `ref`/`reactive` + 若干函数 + 生命周期写在一起，可抽成 **composable**（如 useRequest、useTable）复用。
- 类型推导更好，TS 友好。
- 与 React Hooks 类似，但 Vue 的响应式是「代理式」，没有 Hooks 的闭包陷阱和依赖数组，写起来更直观。

**为什么要有 Composition API？**

- **逻辑复用**：跨组件的逻辑可抽成 composable，不依赖 mixin，没有命名冲突和来源不清晰问题。
- **代码组织**：按功能块组织，而不是按选项类型，大组件更易维护。
- **与 TS 结合**：泛型、推导更自然。
- **与未来结合**：Vue 3 的编译优化（如 Fragment、静态提升）、与 RFC 中的能力都更偏向 Composition API。

**选择建议**：新项目、新组件推荐 Composition API；老项目可渐进迁移，Options API 仍完全支持。

## 11. Vue 的虚拟 DOM 和 diff 算法大致流程？

### 答案要点

**虚拟 DOM**

- 用 JS 对象（VNode）描述真实 DOM 结构，包含 tag、props、children、key 等。组件渲染时先得到 VNode 树，再通过 **patch** 把 VNode 转成或更新为真实 DOM。

**diff 流程（同层比较）**

- Vue 对**同一层**的子节点做 diff，不跨层比较（跨层则视为不同节点，整体替换）。
- **单节点**：新旧都有且 sameVNode（tag + key 一致）则 patch 更新；否则删旧建新。
- **列表节点**：
  - 头头、尾尾、头尾、尾头 四种简单比较，能复用就移动；
  - 否则用 **key → index** 的 Map 找可复用节点，通过移动或新建/删除，使新顺序与 newChildren 一致。
- **key 的作用**：在「列表 diff」里用 key 找可复用节点，减少 DOM 操作；key 不稳定会导致复用错节点、状态错乱。

**为什么需要虚拟 DOM？**

- 把「视图」抽象成数据，方便做跨平台（weex、小程序等）；集中做 diff 后批量更新 DOM，避免手写大量 DOM 操作；配合响应式，数据变 → 生成新 VNode 树 → diff → 最小化更新 DOM。

## 12. Vue 3 的 Teleport 是做什么的？典型场景？

### 答案要点

**作用**

- 把组件**模板里的一段 DOM** 渲染到**其他 DOM 节点**（如 body、#modal-root），而不改变组件的逻辑位置（仍属于当前组件的子树，父子关系、provide/inject、事件等不变）。

**用法**

```vue
<template>
  <div>
    <Teleport to="body">
      <div class="modal">...</div>
    </Teleport>
  </div>
</template>
```

- `to` 可以是 CSS 选择器或元素引用；可配合 `disabled` 条件控制是否「传送」。

**典型场景**

- **弹层/Modal**：避免被父级 `overflow: hidden` 或 `z-index` 裁剪，挂到 body 下统一管理层级。
- **Toast/Notification**：挂到顶层容器，避免被布局影响。
- **全屏/浮层**：需要脱离当前布局流时使用。

**注意**：Teleport 只移动 DOM 位置，不改变组件树；事件、插槽、provide/inject 仍按组件树关系工作。

## 13. Vue 里如何做性能优化？（列举常见手段）

### 答案要点

**代码与结构**

- **v-if / v-show**：频繁切换用 v-show，否则用 v-if 减少不必要节点。
- **computed 缓存**：能算出来的用 computed，避免在模板里写方法或复杂表达式。
- **列表**：加稳定 key；大列表用虚拟滚动（只渲染可视区）；避免 v-if 和 v-for 同写在一个元素上（v-for 优先级高，会重复判断 v-if）。
- **按需引入**：组件库、图标按需加载，减少首包体积。
- **异步组件**：`defineAsyncComponent` 或路由懒加载，拆包。

**运行时**

- **keep-alive**：对列表详情、Tab 等做组件缓存，减少重复创建。
- **避免深层响应式**：大对象可 shallowRef 或只把需要响应的部分包成 reactive。
- **事件与定时器**：在 onUnmounted 里移除监听、清定时器，防泄漏。

**构建与加载**

- **生产关 source map**、压缩、Tree Shaking。
- **CDN 大库**、预加载关键资源、骨架屏。

**监控**

- 用 Vue DevTools、Performance 看组件耗时与重复渲染，针对性优化。
